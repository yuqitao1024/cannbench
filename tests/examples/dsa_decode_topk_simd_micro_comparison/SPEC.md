# DSA Decode TopK SIMT VF vs SIMD Micro API Specification

## Goal

Measure whether rewriting the retained DSA v3.2 decode TopK example's five
SIMT VF stages with SIMD Micro API improves the fixed realistic decode case,
without changing the distributed radix algorithm or the measured kernel
boundary.

This is an isolated example under `tests/examples/`. It does not change the
production lightning-indexer operator.

## Frozen Contract

- Input: BF16 scores with shape `[4, 32768]`.
- Output: INT32 selected indices with shape `[4, 2048]`.
- Context partition: 16 shards per row, 2,048 scores per shard.
- Launch: one vector kernel with 64 blocks.
- Dynamic UB: 45,056 bytes with the retained score shard, two staged
  histogram-shard regions, and stage scratch layout.
- GM workspaces: high histogram, low histogram, row state, and shard offsets
  retain the baseline shapes and types.
- Host input: deterministic BF16 scores generated by `host_common.h`.
- Oracle: every row must contain 2,048 unique in-range indices with the exact
  top-k score multiset, including the required number of threshold ties.
- Timing boundary: the single physical TopK kernel only. Host allocation,
  host/device copies, and verification are outside the profiler duration.

## Compared Implementations

### Frozen SIMT v2 baseline

`simt_v2_topk.asc` is copied byte-for-byte from
`tests/examples/dsa_decode_topk_comparison/simt_v2_topk.asc` at repository
revision `ccdcfed17aa01b607ffe0869a8a324d32df83833`, with SHA-256
`d0f5821eeb739d00c2ab783c0bc19a401a1500e3b5918746b0c8d07ded13a0ae`.
It retains:

1. one GM-to-UB DMA of each 2,048-element score shard;
2. distributed high-byte inclusive-suffix histograms;
3. row-level high-threshold reduction;
4. distributed low-byte inclusive-suffix histograms;
5. row-level low-threshold and deterministic shard-offset construction;
6. stable shard-local compaction;
7. five SIMT VF calls and four `AscendC::SyncAll()` boundaries.

### SIMD Micro API candidate

`simd_micro_topk.asc` retains the same outer 64-block kernel, one score DMA,
four device-wide phase barriers, GM publication points, workspace addresses,
and five logical stages. Only stage implementation changes:

1. High histogram uses aligned Micro API loads, sortable BF16 key conversion,
   and `MicroAPI::Histograms`.
2. High reduction combines the 16 shard histograms and identifies the same
   inclusive-suffix threshold.
3. Low histogram uses Micro API compare masks and
   `MicroAPI::Histograms` for the selected high byte.
4. Low reduction selects the low byte and constructs the same exclusive
   per-shard greater/equal offsets.
5. Compact uses Micro API compare, squeeze, and unaligned-store primitives to
   preserve ascending context-index order inside each shard before applying
   the existing shard offsets.

The candidate must not call a `__simt_vf__`, use the four-block vLLM
sort/merge algorithm, add a physical kernel, read scores directly from GM in
a stage, or change the host data and oracle.

Micro API has no direct equivalent for the baseline's warp shuffle prefix and
warp-atomic reservation protocol. Fixed-size UB staging and scalar control in
the enclosing vector kernel are allowed for those two bookkeeping operations,
provided the five-stage dataflow, deterministic output contract, launch, GM
workspace, synchronization, and timing boundary remain unchanged. Such work
is part of the candidate kernel duration.

## Considered Alternatives

1. **Same-dataflow staged SIMD (selected).** This isolates the programming
   model while preserving the distributed radix work decomposition. Some
   fixed-size scalar bookkeeping may limit SIMD speedup, but the comparison is
   attributable.
2. **Reuse the vLLM four-block Micro API TopK.** This is already represented by
   the existing vLLM comparison and changes algorithm, launch geometry, and
   work partition, so it cannot answer the SIMT-VF versus SIMD question.
3. **Create separate kernels per SIMD stage.** This simplifies coordination but
   changes the one-kernel boundary and adds launch overhead, invalidating the
   requested comparison.

## Source Contract Tests

The example-local pytest file must verify:

- the exact deliverable set and two CMake targets;
- fixed shape, dtype, 64-block launch, and 45,056-byte UB constants;
- the baseline source hash matches the frozen retained source;
- both sources have one physical kernel launch and four `SyncAll` calls;
- the candidate has five `__simd_vf__` stage definitions and no
  `__simt_vf__`, `asc_vf_call`, or four-block/vLLM implementation tokens;
- the candidate contains Micro API histogram, compare, squeeze, load, and
  store operations;
- the score shard has exactly one GM-to-UB DMA and all score-consuming stages
  receive a UB pointer;
- profiling scripts use `--aic-metrics=Default --launch-count=1`, do not set
  profiler warmup, and do not use `--kernel-name`.

profiling. Profile ten alternating-order baseline/candidate pairs. Odd pairs
run baseline first; even pairs run candidate first. Every sample uses:

```bash
msopprof --output=<unique-directory> \
  --aic-metrics=Default --launch-count=1 <executable>
```

Do not set profiler warmup and do not pass `--kernel-name`. Accept a sample
only when the raw profile contains exactly one exact target-kernel row with
block dimension 64 and execution-time current/rated frequency
`1650/1650 MHz`.

Report all 20 durations, medians, min/max, paired candidate-minus-baseline
deltas, paired wins/ties, and candidate improvement percentage. A performance
gain is retained as an observation only when correctness holds, the candidate
median is lower, and it wins a clear majority of the ten pairs. Regardless of
the result, keep the candidate as an experimental comparison and document
whether it won or regressed.
